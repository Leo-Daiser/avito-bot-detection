# Avito Bot Detection

Решение задачи детекции автоматизированного трафика по истории пользовательских событий.

Для каждой `cookie_id` модель возвращает `score` от 0 до 1: чем выше значение, тем больше оснований считать трафик автоматизированным.

## Result

**Hidden test: Precision@Recall≥0.70 = 0.80348**

Для сравнения, константный baseline на том же тесте: **0.09391**.

## Task

Даны метаданные cookie и журнал пользовательских событий за ограниченное временное окно.

Целевая переменная:

- `target = 1` — автоматизированный трафик;
- `target = 0` — человеческий трафик.

Основная метрика:

```text
max Precision(t), при Recall(t) >= 0.70
```

То есть модель должна находить не меньше 70% автоматизированного трафика и при этом максимизировать precision.

## The main trap: temporal leakage

Самая важная находка в данных — наличие событий после окончания разрешённого окна наблюдения.

Для каждого объекта можно использовать только события, удовлетворяющие условию:

```python
window_start_ts <= event_ts < window_end_ts
```

В исходном `events.csv.gz` были события за пределами этого интервала.

Среди них встречался `captcha_shown`, сильно связанный с положительным классом. Если агрегировать всю историю событий без фильтрации по окну, модель получает информацию из будущего и локальная оценка становится невалидной.

Поэтому фильтрация по временному окну выполняется **до feature engineering**.

## Validation strategy

Test расположен позже train по времени, поэтому случайный `train_test_split` плохо имитирует реальное использование модели.

Использовалась временная валидация:

**past → future**

Дополнительно модель проверялась на нескольких длинных out-of-time holdout, близких по длине к реальному тестовому периоду.

| Validation period | Precision@Recall≥0.70 |
|---|---:|
| Apr 11–19 | 0.704 |
| Apr 12–19 | 0.760 |
| Apr 13–19 | 0.751 |
| Apr 14–19 | 0.776 |
| **Mean** | **0.748** |

ROC-AUC на этих разбиениях держался примерно на уровне **0.93–0.94**.

Hidden test оказался выше локальной оценки: **0.80348**.

## Feature engineering

Исходный event-log агрегируется до уровня `cookie_id`.

Финальная модель использует **105 признаков**.

### Activity

Используются:

- общее число событий;
- число уникальных событий;
- количество разных типов действий;
- число активных минут и часов;
- показатели интенсивности активности;
- число и доля полных дублей событий.

### Temporal behaviour

Для последовательных событий считаются интервалы между действиями:

- `mean`, `std`, `min`, `max`, `median`;
- `q10`, `q25`, `q75`, `q90`;
- доля интервалов меньше 5, 10, 30, 60, 300 и 900 секунд;
- продолжительность активного периода;
- число событий на активную минуту.

Эта группа признаков оказалась одной из самых сильных: автоматизированный трафик часто отличается от человеческого именно ритмом действий.

### Items, categories and locations

Используются:

- число уникальных `item_id`;
- число категорий;
- число локаций;
- число типов продавцов;
- `events_per_item`;
- `events_per_category`;
- `events_per_location`;
- `locations_per_category`.

### Search behaviour

Используются:

- число уникальных поисковых запросов;
- статистики `search_page`;
- доля событий с поисковыми полями.

### Pointer behaviour

Считаются:

- статистики `pointer_x` и `pointer_y`;
- диапазоны координат;
- расстояния между последовательными pointer-событиями.

Pointer-признаки дали дополнительный сигнал и вошли в число наиболее полезных признаков.

### Behaviour diversity

Для нескольких типов активности считается entropy:

- event entropy;
- category entropy;
- location entropy;
- query entropy.

Это позволяет оценить, насколько поведение сосредоточено вокруг небольшого числа повторяющихся паттернов.

### Cookie metadata

В модель входит возраст cookie к началу окна:

```text
cookie_age_hours
```

Этот признак показывал стабильное разделение классов на разных временных участках train.

## Duplicate events

В event-log присутствовали полные дубликаты строк.

Они не удаляются безусловно, потому что сама повторяемость может быть частью поведения автоматизированного клиента.

Поэтому:

- количество дублей используется как отдельный признак;
- для временных последовательностей и pointer trajectory используются уникальные события.

Так технический дубль не создаёт искусственный `0 sec` gap между событиями.

## Baseline

В качестве отправной точки использовался простой `RandomForestClassifier` на небольшом наборе агрегированных признаков.

| Model | Precision@Recall≥0.70 | ROC-AUC |
|---|---:|---:|
| Simple Random Forest | ~0.106 | ~0.61 |
| Final solution | ~0.75 local / **0.80348 hidden** | ~0.94 local |

Большая часть прироста появилась не из-за тюнинга модели, а после корректной обработки времени и построения поведенческих признаков.

## Model

Финальная модель — ансамбль из пяти `CatBoostClassifier`.

Основные параметры:

```python
depth = 6
learning_rate = 0.05
iterations = 600
l2_leaf_reg = 5
random_strength = 0.8
```

Используются пять фиксированных seed:

```python
[17, 42, 137, 777, 2026]
```

Финальный `score` — среднее предсказанных вероятностей пяти моделей.

Ансамбль используется прежде всего для снижения зависимости результата от случайности отдельного запуска CatBoost.

## What I tried and rejected

Во время разработки проверялись несколько альтернатив.

| Experiment | Result |
|---|---|
| User-Agent features | нестабильный прирост на temporal validation |
| Расширенный набор ~150 признаков | лучше на отдельных коротких folds, хуже на длинных holdout |
| CatBoost `depth=7` | похожий ROC-AUC, хуже стабильность основной метрики |
| Rank averaging | немного хуже обычного probability averaging |
| 400 / 500 iterations | в среднем хуже 600 iterations |
| Multiple random seeds | снизили зависимость результата от конкретной инициализации |

Главный принцип при выборе финального решения — **не максимальный score на одном fold, а устойчивость на нескольких будущих временных интервалах**.

```bash

```

Основное окружение:

```text

```

Все random seed и параметры финальной модели зафиксированы.

Notebook полностью выполняет pipeline:

```text
data loading
    ↓
time-window filtering
    ↓
feature engineering
    ↓
temporal validation
    ↓
model training
    ↓
ensemble
    ↓

```

Перед сохранением submission дополнительно проверяются:

- количество строк;
- уникальность `cookie_id`;
- отсутствие пропущенных `score`;
- диапазон `score` от 0 до 1;
- порядок cookie;
- соответствие `sample_submission`.

## Key takeaway

Главный результат этой задачи — качество определил не сложный hyperparameter tuning.

Самый большой эффект дали:

**корректная временная постановка → предотвращение leakage → behavioural feature engineering → честная out-of-time validation**

Более сложная модель или большее число признаков не обязательно давали лучший результат. Несколько раз более простой вариант оказывался лучше именно после проверки на будущих временных интервалах.

## Limitations

Это офлайн-решение.

Для production-системы дополнительно понадобились бы:

- мониторинг data/concept drift;
- контроль появления новых типов автоматизации;
- latency feature pipeline;
- выбор рабочего threshold с учётом стоимости false positives;
- регулярная переоценка качества на новых данных;
- отдельная проверка calibration.

Выход CatBoost здесь используется как ranking score и не должен автоматически интерпретироваться как идеально откалиброванная вероятность.
